# 7. Data Governance — กติกาและความรับผิดชอบต่อข้อมูล

[สารบัญ](README.md) · [บทก่อนหน้า](data-lifecycle.md) · [บทถัดไป](sql-vs-nosql.md)

## Data Governance คืออะไร

Data Governance คือการกำหนดว่าใครรับผิดชอบข้อมูล ข้อมูลหมายถึงอะไร ใครใช้ได้ ใช้ภายใต้กติกาใด และดูแลตลอดอายุข้อมูลอย่างไร เพื่อให้ข้อมูลเชื่อถือได้และใช้งานได้ตรงวัตถุประสงค์

ไม่ใช่เพียงติดตั้งเครื่องมือหรือเขียนนโยบายแล้วจบ ต้องมีผู้ตัดสินใจ วิธีนำกฎไปใช้ หลักฐานตรวจสอบ และกระบวนการแก้ปัญหา สำหรับโปรเจกต์เล็ก คนเดียวอาจรับหลายบทบาทได้ ไม่จำเป็นต้องเริ่มจากโครงสร้างองค์กรขนาดใหญ่

## ต่างจาก Database Design อย่างไร

| เรื่อง | คำถาม | ตัวอย่าง |
|---|---|---|
| Data Governance | ใครกำหนดกฎ และเหตุใดต้องใช้กฎนี้? | ฝ่ายการเงินนิยามยอดรับสุทธิ |
| Database Design | จะจัดข้อมูลและบังคับกฎอย่างไร? | แยก payments กับ refunds และกำหนด Constraints |
| Data Management | จะดำเนินงานตามกฎอย่างไร? | นำเข้า สำรอง กู้คืน ตรวจคุณภาพ และเก็บถาวร |

ทั้งสามเรื่องทำงานร่วมกัน การมี Foreign Key ไม่ได้ตอบว่าใครมีอำนาจแก้นิยามข้อมูล และการมีนโยบายก็ไม่รับรองว่าโปรแกรมบังคับกฎครบ

## ด้านที่ควรกำหนด

| ด้าน | สิ่งที่ต้องตอบ | ตัวอย่างในร้านค้าออนไลน์ |
|---|---|---|
| Ownership | ใครรับผิดชอบและตัดสินใจ? | ผู้รับผิดชอบข้อมูลการชำระเงิน |
| Definitions | คำและตัวเลขมีความหมายอะไร? | ยอดขายต่างจากยอดรับเงินจริงอย่างไร |
| Quality | ถูกต้อง ครบ ไม่ซ้ำ และทันเวลาตามเกณฑ์หรือไม่? | รายการรับเงินต้องมีสกุลเงิน |
| Access | ใครอ่าน แก้ ส่งออก หรือแบ่งปันได้? | เจ้าหน้าที่เห็นเฉพาะบริษัทที่ดูแล |
| Lifecycle | เก็บนานเท่าไร Archive และลบอย่างไร? | จัดการธุรกรรม Audit, Backup และไฟล์ส่งออก |
| Lineage | ข้อมูลมาจากไหน ผ่านการแปลงอะไร? | CSV → Staging → payments → รายงาน |
| Change control | ใครอนุมัติการเปลี่ยนความหมายหรือโครงสร้าง? | เปลี่ยนสูตรรายงานและแจ้งผู้ใช้งาน |

## บทบาทที่พบได้บ่อย

- **Data Owner:** รับผิดชอบด้านธุรกิจ ตัดสินนิยาม การใช้งาน และยอมรับข้อยกเว้นตามอำนาจที่องค์กรกำหนด
- **Data Steward:** ดูแลความหมาย Metadata และคุณภาพ ประสานแก้ปัญหาข้อมูล
- **ผู้ดูแลทางเทคนิค:** นำสิทธิ์ Constraints, Backup และกลไกดูแลไปใช้จริง
- **ผู้ใช้ข้อมูล:** ใช้ตามวัตถุประสงค์และแจ้งปัญหาที่พบ

ชื่อและขอบเขตบทบาทอาจต่างกันแต่ละองค์กร สิ่งสำคัญคือแต่ละงานมีผู้รับผิดชอบชัด ไม่ใช่บังคับให้มีตำแหน่งครบตามชื่อ

## ตัวอย่างปัญหา: ทุกทีมเขียน SQL ถูก แต่ยอดไม่ตรง

ฝ่ายขายรวมคำสั่งซื้อที่ยืนยันแล้ว ส่วนฝ่ายการเงินรวม Payment ที่สำเร็จหัก Refund ที่สำเร็จ ทั้งสองยอดอาจถูกต้องตามนิยามของตัวเอง แต่ไม่ควรเรียกชื่อเดียวกันโดยไม่อธิบาย

พจนานุกรมตัวชี้วัดควรระบุอย่างน้อย:

| รายการ | ตัวอย่างนิยามเพื่อฝึก |
|---|---|
| ชื่อ | ยอดรับสุทธิ |
| สูตร | ยอด Payment สำเร็จ − ยอด Refund สำเร็จ |
| หน่วย | แยกตาม currency ไม่รวมข้ามสกุลโดยตรง |
| เวลา | กำหนดว่าจะใช้เวลารับเงินจริงหรือเวลาลงบันทึก และเขตเวลาใด |
| แหล่งข้อมูล | payments และ refunds |
| ข้อยกเว้น | pending/unknown ยังไม่ถือว่าสำเร็จ |
| ผู้รับผิดชอบ | บทบาทที่กำหนดนิยามและตอบข้อสงสัย |
| เวอร์ชัน | วันที่เริ่มใช้สูตร และวิธีจัดการรายงานเดิม |

สูตรนี้เป็นตัวอย่าง ไม่ใช่นิยามบัญชีสากล ต้องตกลงตามวัตถุประสงค์ของรายงานจริง

## Data Dictionary และ Business Glossary

Business Glossary อธิบายคำธุรกิจ เช่น ลูกค้าที่ใช้งานอยู่ ส่วน Data Dictionary ลงรายละเอียดตารางและคอลัมน์ เช่น ชนิดข้อมูล คีย์ ความหมาย NULL และค่าที่อนุญาต ควรเชื่อมกันเพื่อให้ผู้ใช้เข้าใจว่าคำธุรกิจมาจากฟิลด์ใด

ตัวอย่าง `payments.paid_at`: เวลาที่ผู้ให้บริการยืนยันว่ารับเงินสำเร็จ ไม่ใช่เวลาที่ระบบรับ webhook หากยังไม่ทราบผลให้เป็น NULL ตามกฎที่กำหนด

## คุณภาพข้อมูลต้องมีเกณฑ์และเจ้าของปัญหา

| กฎตัวอย่าง | วิธีตรวจหรือบังคับ |
|---|---|
| สกุลเงินต้องมี | NOT NULL และ Foreign Key ตามขอบเขตที่ออกแบบ |
| รหัสคำขอไม่ซ้ำภายในบริษัท | UNIQUE(tenant_id, request_id) |
| รับเงินสำเร็จต้องมีเวลายืนยัน | CHECK ร่วมกับ NOT NULL ของ status |
| รายงานต้องตามข้อมูลไม่เกินเวลาที่ตกลง | ติดตามความล่าช้าและแจ้งผู้รับผิดชอบ |
| reserved ต้องตรงกับรายละเอียดที่นับตามกฎ | งาน reconciliation ที่ใช้ข้อมูลสอดคล้องกัน |

เมื่อพบปัญหา ให้บันทึกผลกระทบ ตรวจสาเหตุ กำหนดวิธีซ่อมและป้องกันซ้ำ อย่าแก้ตัวเลขให้ตรงโดยไม่รู้ว่ารายละเอียดหรือยอดสรุปส่วนใดผิด

## สิทธิ์และวงจรชีวิต

จำแนกข้อมูลตามความละเอียดอ่อนและวัตถุประสงค์ เช่น ข้อมูลเผยแพร่ได้ ข้อมูลภายใน หรือข้อมูลจำกัดการเข้าถึง แล้วกำหนดสิทธิ์อ่าน แก้ ส่งออก และการใช้งานในเครื่องทดสอบให้เหมาะสม

อายุการเก็บต้องมีเหตุผลและผู้รับผิดชอบ ไม่กำหนดจำนวนปีเหมารวมในทุกระบบ พิจารณาข้อกำหนดที่ใช้จริง รวมถึงข้อมูลใน Snapshot, Audit, Backup, Archive และไฟล์ส่งออก Soft Delete ไม่ได้แปลว่าลบข้อมูลออกจากทุกสำเนาแล้ว

ตัวอย่างเชื่อมกับ Idempotency: หาก Archive คำสั่งซื้อแล้วตรวจคำขอซ้ำเฉพาะตารางปัจจุบัน ระบบอาจสร้างคำสั่งซื้อเดิมซ้ำ ต้องกำหนดช่วงรับรองการป้องกันซ้ำและวิธีเก็บหลักฐานให้ครอบคลุม

## Lineage และการเปลี่ยนแปลง

สำหรับการฝึกด้วย Dataset เก็บที่มา เวอร์ชันไฟล์ วันที่นำเข้า และกฎแปลง รวมถึงเงื่อนไขการใช้ข้อมูลตามแหล่งนั้น การมีไฟล์ดาวน์โหลดได้ไม่ได้หมายความว่าเผยแพร่ต่อได้ทุกแบบ

แยกกฎที่พบจากข้อมูลออกจากกฎที่สมมติเพื่อฝึก หากเปลี่ยนสูตรหรือ Mapping ควรทราบว่ากระทบรายงานและผู้ใช้ใดบ้าง และเก็บเวอร์ชันที่จำเป็นต่อการตรวจย้อนหลัง

## เริ่มทำแบบพอดีกับโปรเจกต์

เริ่มจากเอกสารสั้นหนึ่งชุดที่มีชื่อข้อมูล ความหมาย ผู้รับผิดชอบ แหล่งที่มา ผู้มีสิทธิ์ใช้ กฎคุณภาพ และนโยบายเก็บข้อมูล ผูกกฎสำคัญกับ Constraint หรือกระบวนการที่ตรวจได้ แล้วทบทวนเมื่อเปลี่ยน Schema หรือการใช้งาน

| คำถามทบทวน | หลักฐานที่ควรมี |
|---|---|
| ใครตัดสินนิยามนี้? | ผู้รับผิดชอบหรือบทบาทที่ระบุไว้ |
| ตัวเลขมาจากไหน? | แหล่งข้อมูล สูตร และเวอร์ชัน |
| รู้ได้อย่างไรว่าข้อมูลผิด? | กฎคุณภาพและวิธีตรวจ |
| ใครใช้ได้? | กติกาสิทธิ์และการตั้งค่าที่นำไปใช้จริง |
| เมื่อเลิกใช้แล้วทำอย่างไร? | นโยบายเก็บ Archive และลบ |

## แบบฝึกหัด

ใช้ระบบยืมหนังสือจาก Workshop กำหนดเจ้าของข้อมูลสมาชิก นิยามสมาชิก active ผู้ที่แก้ประวัติยืมได้ และวิธีดูแลข้อมูลเมื่อสมาชิกปิดบัญชี จากนั้นระบุว่ากฎใดใช้ Constraint กฎใดต้องใช้สิทธิ์หรือขั้นตอนทำงาน และใครรับผิดชอบเมื่อพบปัญหา
