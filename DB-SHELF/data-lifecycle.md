# 6. สถานะและวงจรชีวิตข้อมูล

[สารบัญ](README.md) · [บทก่อนหน้า](practical-design.md) · [บทถัดไป](data-governance.md)

## ออกแบบมากกว่ารายชื่อสถานะ

สถานะควรมีความหมายชัด: ใครเปลี่ยนได้ จากสถานะใด ไปสถานะใด ต้องตรวจอะไร และมีผลอะไรตามมา ตัวอย่างกฎสำหรับคำสั่งซื้อหนึ่งระบบ:

| จาก | ไป | เงื่อนไขตัวอย่าง |
|---|---|---|
| draft | confirmed | มีรายการและยืนยันราคาแล้ว |
| confirmed | cancelled | ยังไม่เริ่มจัดส่ง และจัดการเงินตามนโยบาย |
| confirmed | shipped | พร้อมจัดส่งและผ่านกฎการชำระเงิน |
| shipped | completed | ส่งมอบสำเร็จ |

กฎนี้เป็นตัวอย่าง ไม่ใช่มาตรฐานสำหรับทุกธุรกิจ การจ่ายเงิน การจัดส่ง และตัวคำสั่งซื้ออาจมีวงจรชีวิตแยกกัน ไม่ควรรวมทุกชุดเป็นสถานะเดียวจนเกิดค่าผสมจำนวนมาก

## บังคับ Transition

```sql
UPDATE orders
SET status = 'confirmed'
WHERE order_id = :order_id AND status = 'draft'
RETURNING order_id;
```

ตรวจจำนวนแถว แล้วเพิ่มประวัติใน Transaction เดียวกัน หากต้องตรวจรายการลูกด้วยต้องเลือก Lock และ isolation ให้ตรงกฎ CHECK ที่ตรวจรายชื่อสถานะไม่รับรองลำดับการเปลี่ยน

หากหลายโปรแกรมเขียนโดยตรง อาจรวมการเปลี่ยนสถานะไว้ในฟังก์ชันฐานข้อมูลและจำกัดสิทธิ์ หรือใช้ Trigger ตามความเหมาะสม อย่าสมมติว่าทุกเส้นทางจะผ่านหน้าจอเดียวกัน

## วงจรชีวิตหลังเลิกใช้งาน

แยกการหยุดขาย การปิดบัญชี การยกเลิกธุรกรรม การเก็บถาวร และการลบจริง เพราะมีผลต่างกัน Soft Delete ไม่ได้ลดขนาดข้อมูลเอง และไม่ใช่การลบข้อมูลส่วนบุคคลออกจากทุกสำเนา

กำหนดนโยบายให้แต่ละกลุ่ม: ใครเข้าถึงได้ เก็บนานเท่าไร เมื่อไรย้ายออก และ Snapshot, Audit, Backup หรือไฟล์ส่งออกต้องจัดการอย่างไร ระยะเวลาเก็บให้ยึดความต้องการและข้อกำหนดที่ใช้กับระบบจริง

## แบบฝึกหัด

ออกแบบกฎยกเลิกคำสั่งซื้อก่อนจ่าย หลังจ่าย และหลังส่งสินค้า ระบุว่าต้องเปลี่ยนสถานะอะไร และต้องสร้างเหตุการณ์คืนเงินหรือคืนสินค้าต่างหากเมื่อใด
