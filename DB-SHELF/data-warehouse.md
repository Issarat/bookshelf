# 23. Data Warehouse — ออกแบบข้อมูลเพื่อวิเคราะห์

[สารบัญ](README.md) · [บทก่อนหน้า](sharding.md) · [บทถัดไป](data-lake.md)

## Data Warehouse คืออะไร

Data Warehouse เป็นระบบข้อมูลที่จัดเตรียมไว้เพื่อวิเคราะห์และรายงาน โดยรวมข้อมูลจากแหล่งที่ต้องใช้และกำหนดความหมายให้ตรงกัน เช่น ยอดขายตามวัน หมวดสินค้า และช่องทางขาย เป้าหมายต่างจากฐานข้อมูลที่รองรับการทำธุรกรรมรายครั้ง ([AWS: Data Warehouse](https://aws.amazon.com/what-is/data-warehouse/))

ไม่ต้องรอให้มี Big Data จึงจะมี Warehouse และการนำตารางมารวมไว้ที่เดียวโดยไม่มีนิยามหรือการตรวจคุณภาพ ยังไม่ได้ทำให้รายงานเชื่อถือได้

## OLTP กับ OLAP

| ประเด็น | OLTP: ระบบทำธุรกรรม | OLAP: งานวิเคราะห์ |
|---|---|---|
| คำถาม | ลูกค้าคนนี้จ่ายสำเร็จหรือยัง? | ยอดขายแต่ละหมวดเปลี่ยนอย่างไรในรอบปี? |
| รูปแบบงาน | อ่าน/เขียนรายการขนาดเล็กจำนวนมาก | อ่านหลายรายการแล้วกรอง รวม หรือเปรียบเทียบ |
| จุดสำคัญ | ความถูกต้องของธุรกรรมและเวลาตอบสนอง | ความหมายตัวชี้วัด ความครบ และประสิทธิภาพวิเคราะห์ |
| โครงสร้างตัวอย่าง | orders, order_items, payments | Facts และ Dimensions |

คำเหล่านี้บอกลักษณะงาน ไม่ได้รับรองว่าผลิตภัณฑ์หนึ่งทำได้เพียงแบบเดียว สำหรับการฝึกอาจแยก schema ใน PostgreSQL ก่อน ส่วนงานจริงต้องประเมินผลกระทบและขอบเขตทรัพยากร เพราะแยก schema ยังใช้เครื่องและทรัพยากรร่วมกัน

## Star Schema: Fact และ Dimension

**Fact** เก็บเหตุการณ์หรือค่าที่วัดได้ ส่วน **Dimension** เก็บบริบทสำหรับกรองและจัดกลุ่ม เช่น สินค้า วันที่ และสาขา โครงสร้างแบบ Star Schema ใช้ Dimension เชื่อมเข้าหา Fact ([Microsoft: Star Schema](https://learn.microsoft.com/en-us/power-bi/guidance/star-schema))

| ตารางตัวอย่าง | หนึ่งแถวแทนอะไร |
|---|---|
| fact_sales | หนึ่งบรรทัดสินค้าที่ขายตาม Grain ที่กำหนด |
| dim_product | หนึ่งสินค้าหรือหนึ่งเวอร์ชันของสินค้า ตามนโยบายประวัติ |
| dim_date | หนึ่งวันที่ใช้วิเคราะห์ |
| dim_store | หนึ่งสาขาหรือเวอร์ชันของสาขา |

ตัวอย่างสำหรับร้านค้าสมมติ ไม่ใช่การเพิ่มคอลัมน์ที่ไม่มีใน Olist:

```text
fact_sales(sale_line_key, source_order_id, line_no,
           product_key, date_key, store_key,
           quantity, gross_amount, discount_amount, currency)
```

กำหนด Grain ก่อนเลือก Measure หากหนึ่งแถวเป็นบรรทัดสินค้า อย่าใส่ยอดชำระทั้งคำสั่งซื้อซ้ำทุกแถว การนับคำสั่งซื้อจาก Fact นี้ก็ต้องพิจารณารหัสคำสั่งซื้อ ไม่ใช้ COUNT(*) แทนโดยตรง

## ตัวชี้วัดรวมอย่างไร

ยอดเงินรวมได้เมื่อสกุลเงินและนิยามสอดคล้องกัน ส่วนอัตราร้อยละหรือราคาเฉลี่ยไม่ควร SUM ตรง ๆ เช่น อัตราคืนสินค้าโดยรวมควรคำนวณจากยอดฐานที่เหมาะสม ไม่เฉลี่ยเปอร์เซ็นต์ของทุกสาขาโดยไม่ถ่วงน้ำหนัก

แยก Fact การขาย การรับเงิน และการคืนเงินตามเหตุการณ์ หากต้องรายงานร่วมกัน ให้รวมให้อยู่ Grain เดียวกันก่อน JOIN เพื่อลดปัญหาคูณจำนวนแถว เหมือนที่เรียนใน [บทคำสั่งซื้อและการชำระเงิน](orders-payments-and-events.md)

## ประวัติ Dimension

ถ้าสินค้าเปลี่ยนหมวด ต้องตัดสินว่ารายงานเก่าจะใช้หมวดปัจจุบันหรือหมวด ณ วันที่ขาย:

- **Type 1:** เขียนทับข้อมูลเดิม เหมาะเมื่ออยากวิเคราะห์ตามค่าปัจจุบันหรือแก้ข้อมูลผิดตามนโยบาย
- **Type 2:** สร้างเวอร์ชันใหม่พร้อมช่วงเวลาที่มีผล และให้ Fact เชื่อมเวอร์ชันที่ถูกต้อง

Type 2 ต้องตรวจช่วงเวลาทับซ้อนและรายการที่มาช้า ไม่ใช่เพียงเพิ่ม valid_from/valid_to แล้วถือว่าประวัติถูกต้องครบ

## ETL, ELT และ Data Mart

ETL คือ Extract → Transform → Load ส่วน ELT นำเข้าก่อนแล้วแปลงในระบบปลายทาง การเลือกขึ้นกับสิทธิ์ เครื่องมือ และขอบเขตข้อมูล การ Load ก่อนยังต้องควบคุมข้อมูลละเอียดอ่อนและคุณภาพก่อนนำไปใช้

Data Mart คือชุดข้อมูลเพื่อกลุ่มงานเฉพาะ เช่น การเงินหรือการตลาด ต้องรักษานิยามร่วม เช่น currency, วันตัดยอด และรหัสลูกค้า ไม่ให้แต่ละทีมใช้ชื่อยอดเดียวกันแต่คำนวณคนละสูตรโดยไม่รู้ตัว

## เชื่อมกับ Workshop Kaggle

ใช้ผล Migration ที่ผ่าน Reconciliation เป็นแหล่งหนึ่งของการสร้างรายงาน ออกแบบ Fact รายการสินค้าและ Fact การจ่ายแยกกัน เก็บ source keys ให้ตรวจย้อนกลับได้ แล้วเทียบยอดก่อนและหลังสร้าง Warehouse

ไม่ควรยืนยันสถานะรับเงินจริงหรือสกุลเงินจากการเดา หาก Dataset ไม่ให้ข้อมูลนั้น ให้ระบุข้อจำกัดของรายงานตามจริง

## แบบฝึกหัด

ออกแบบรายงานยอดสินค้าต่อเดือนและจำนวนคำสั่งซื้อต่อหมวด ระบุ Grain ของ Fact, Dimensions, นิยามยอด และวิธีนับคำสั่งซื้อที่มีสินค้าหลายหมวด จากนั้นอธิบายว่าหากสินค้าเปลี่ยนหมวด จะรายงานอดีตตามกฎใด
