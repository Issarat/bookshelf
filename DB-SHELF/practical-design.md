# 5. ออกแบบให้พอดีและแบบฝึกหัด

## Overengineering ใน DB Design

เกิดเมื่อเพิ่มความซับซ้อนเพื่ออนาคตที่ยังไม่มีความต้องการชัด จนต้นทุนดูแลมากกว่าประโยชน์ หัวข้อขั้นสูงที่เรียนเป็นเครื่องมือ ไม่ใช่รายการที่ทุกระบบต้องมี

| งานปัจจุบัน | เริ่มจาก | เพิ่มเมื่อมีเหตุผล |
|---|---|---|
| หมวดหมู่เล็ก | parent_id | Closure Table |
| บริษัทเดียว | โครงสร้างธุรกิจปกติ | Multi-tenant และ RLS |
| ราคาปัจจุบันกับราคาซื้อจริง | products + Snapshot ใน order_items | ช่วงเวลาราคาที่ตั้งขาย |
| ต้องรู้สถานะปัจจุบัน | status | ประวัติการเปลี่ยนทุกครั้ง |
| Query ยังเร็ว | Index ตาม Query สำคัญ | Materialized View |

ความเรียบง่ายไม่ใช่การละทิ้งความถูกต้อง คีย์ NOT NULL, Foreign Key, UNIQUE, CHECK และ Transaction ตามกฎสำคัญมักควรมีตั้งแต่แรก

ก่อนเพิ่มกลไกถามว่า:

1. แก้ปัญหาจริงอะไร ยกเหตุการณ์ได้หรือไม่?
2. ถ้ายังไม่ทำ ข้อมูลจะผิด ประวัติจะหาย หรือแค่ยังไม่รองรับอนาคตที่คาดไว้?
3. เพิ่มภายหลังยากแค่ไหน? Index มักเพิ่มได้ แต่ประวัติที่ไม่เคยบันทึกอาจกู้ไม่ได้

## แบบฝึกหัด: ระบบลงทะเบียนเรียน

กฎ: นักเรียนลงได้หลายวิชา วิชาเปิดหลายเทอม ลงซ้ำต่างเทอมได้ แต่ห้ามลงวิชาเดียวกันซ้ำในเทอมเดียวกัน

โครงสร้างเริ่มต้น:

```text
students(student_id, ...)
courses(course_id, ...)
terms(term_id, ...)
course_offerings(course_id, term_id, capacity)
enrollments(student_id, course_id, term_id, enrolled_at)
```

- course_offerings ใช้ Primary Key `(course_id, term_id)`
- enrollments ใช้ Primary Key หรือ UNIQUE `(student_id, course_id, term_id)` และ Composite Foreign Key ไป offering
- ก่อนนับจำนวนและเพิ่มรายการ ให้ล็อก offering ใน Transaction เดียวกัน เพื่อกันสองคนแย่งที่นั่งสุดท้ายจนเกินความจุ

### ยกเลิกแล้วลงใหม่

ถ้าต้องการเพียงสถานะล่าสุด ใช้แถวเดิมแล้วเปลี่ยน status ได้ ถ้าต้องเก็บแต่ละครั้งแยก ใช้ enrollment_id แล้วบังคับเฉพาะรายการ active:

```sql
CREATE UNIQUE INDEX uq_active_enrollment
ON enrollments(student_id, course_id, term_id)
WHERE status = 'active';
```

ต้องนำข้อกำหนด UNIQUE/Primary Key ของสามคอลัมน์แบบเดิมออกตามแผน Migration มิฉะนั้นยังลงซ้ำหลังยกเลิกไม่ได้ และตอนตรวจ capacity ให้นับเฉพาะสถานะที่ใช้ที่นั่งจริง

## ทบทวนคำตอบสำคัญจากบทสนทนา

| คำถาม | หลักคิด |
|---|---|
| UUID กันคู่หนังสือกับผู้เขียนซ้ำไหม? | ไม่ ต้องมี UNIQUE ของคู่ หรือ Composite Primary Key |
| เก็บ due_at ทั้งที่คำนวณได้ไหม? | เก็บ เพราะเป็นข้อตกลงของการยืมครั้งนั้น |
| ลบสินค้าที่มีประวัติซื้ออย่างไร? | ป้องกันลบจริงและปิดใช้งานตามกฎ |
| SUM(DISTINCT amount) แก้ JOIN ซ้ำได้ไหม? | ไม่ คนละรายการอาจยอดเท่ากัน ต้องรวมตามรหัสรายการก่อน |
| Optimistic Lock ชนแล้วส่งทับใหม่เลยไหม? | ไม่ ให้ตรวจข้อมูลล่าสุดก่อน |
| Deadlock ลองใหม่แค่คำสั่งสุดท้ายไหม? | ไม่ ลองใหม่ทั้ง Transaction พร้อมตรวจเงื่อนไขใหม่ |
| Partial Unique บังคับว่าต้องมีหนึ่งได้ไหม? | รับรองไม่เกินหนึ่ง แต่ไม่บังคับว่าต้องมี |

## ขั้นตอนฝึกกับระบบของตัวเอง

เขียนกฎธุรกิจ → กำหนดความหมายของหนึ่งแถว → วาดความสัมพันธ์ → เลือกคีย์และ Constraints → ระบุประวัติที่ต้องรักษา → พิจารณาคำขอพร้อมกัน → เขียน Query หลัก → ตรวจแผนและเพิ่ม Index เท่าที่มีเหตุผล
