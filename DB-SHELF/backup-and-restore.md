# 18. Backup และ Restore

[สารบัญ](README.md) · [บทก่อนหน้า](database-testing.md) · [บทถัดไป](performance-and-maintenance.md)

## กำหนดเป้าหมายก่อนเลือกวิธี

| คำ | คำถามที่ต้องตอบ |
|---|---|
| RPO | ยอมเสียข้อมูลย้อนหลังได้มากแค่ไหน? |
| RTO | ต้องกลับมาใช้งานได้ภายในเท่าไร? |

สำรองสำเร็จไม่ได้แปลว่ากู้คืนสำเร็จ ต้องทดลองกับข้อมูลและเครื่องมือที่ใช้จริง PostgreSQL มีทั้ง logical dump, physical backup และการกู้คืนด้วย WAL เลือกตามเป้าหมายและขนาดระบบ

## ตัวอย่าง Logical Backup

คำสั่งนี้เป็นตัวอย่างสำหรับสภาพแวดล้อมทดลอง ไม่ได้ถูกรันเป็นส่วนหนึ่งของบทเรียน:

```text
pg_dump --format=custom --file=bookshelf.dump --dbname=bookshelf
createdb bookshelf_restore_test
pg_restore --exit-on-error --dbname=bookshelf_restore_test bookshelf.dump
```

เชื่อมต่อด้วย host/user และวิธีรับรองตัวตนตามสภาพแวดล้อม หลีกเลี่ยงใส่รหัสผ่านลงคำสั่งที่ถูกเก็บในประวัติหรือ Log ใช้ฐานข้อมูลปลายทางแยกที่เตรียมไว้ ไม่เขียนทับระบบจริงเพื่อทดลอง

## สิ่งที่ต้องสำรองนอกข้อมูลตาราง

ตรวจ roles และสิทธิ์ extension การตั้งค่า secrets ที่เก็บแยก และไฟล์ภายนอกที่ข้อมูลอ้างถึง การ dump ฐานข้อมูลเดียวไม่ใช่สำเนาครบทั้งระบบ และต้องตรวจความเข้ากันได้ของเวอร์ชันเครื่องมือกับปลายทาง

## Point-in-time Recovery

PITR ต้องมี base backup และ WAL ที่จำเป็นต่อเนื่อง จึงกู้ถึงจุดเวลาที่กำหนดได้ภายในช่วงที่จัดเก็บไว้ ต่างจากการมี dump รายวันอย่างเดียว ต้องทดสอบกระบวนการและเวลาที่ใช้จริง

Replica ไม่แทน Backup เพราะคำสั่งลบผิดอาจถูกส่งต่อไป Replica เช่นเดียวกัน วางสำเนาสำรองแยกขอบเขตความเสียหายและจำกัดสิทธิ์เข้าถึง

## การซ้อมกู้คืน

บันทึกเวลาที่ใช้ ตรวจจำนวนข้อมูลสำคัญ Constraints และสิทธิ์ แล้วทดลอง Query และ workflow เช่น ยืม–คืนหรือสร้างคำสั่งซื้อ ไม่ตรวจเพียงว่าเครื่องมือจบโดยไม่มี error กำหนดผู้รับผิดชอบและตรวจการสำรองล้มเหลวด้วย
