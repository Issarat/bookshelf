# Workshop: ออกแบบระบบยืมหนังสือให้ครบวงจร

[สารบัญ Workshop](README.md) · [สารบัญบทเรียน](../README.md)

## เป้าหมาย

ฝึกเชื่อมการออกแบบตารางกับ Query, Transaction และการดูแลข้อมูล ผลงานควรเป็น Schema และขั้นตอนที่ตรวจสอบได้ ไม่ใช่เพียง ERD ที่เชื่อมตารางครบ

## 1. กฎธุรกิจและข้อยกเว้น

เริ่มจากหนังสือ สำเนา สมาชิก ผู้เขียน และการยืม กำหนดว่าสมาชิก active ยืมค้างได้ไม่เกิน 5 สำเนา สำเนาต้องพร้อมใช้งานและไม่มีคนยืมค้าง ระบุวันคืน การต่ออายุ การปิดสมาชิก และวิธีแก้รายการบันทึกผิด

หากไม่ต้องเก็บประวัติต่ออายุทุกครั้ง ให้เก็บกำหนดคืนล่าสุดก่อน หากต้องตรวจย้อนหลังจึงเพิ่มประวัติพร้อมเหตุผล

## 2. Grain และ Constraints

เขียนหนึ่งประโยคต่อหนึ่งตารางว่าหนึ่งแถวแทนอะไร จากนั้นออกแบบ Primary Key, Foreign Key, NOT NULL, CHECK และ Partial Unique ของรายการยืมค้าง

ระบุด้วยว่ากฎใดบังคับด้วย Constraint และกฎใดต้องใช้ขั้นตอน Transaction เช่น ขีดจำกัด 5 เล่มและสมาชิกปิดใช้งานแล้วห้ามยืม

## 3. Workflow ยืมและคืน

ก่อนยืม ล็อกสมาชิกและสำเนาตามลำดับที่ตกลง ตรวจสถานะและจำนวน แล้วบันทึกใน Transaction เดียวกัน ทุกเส้นทางที่เปลี่ยนสภาพสำเนาหรือสถานะสมาชิกต้องเข้ากับกติกานี้

เมื่อคืน ใช้เงื่อนไข returned_at IS NULL ตรวจจำนวนแถวที่เปลี่ยนเพื่อไม่ให้คืนซ้ำโดยไม่รู้ตัว กำหนดว่าจะถือคำขอซ้ำเป็นสำเร็จเดิมหรือแสดงว่าเคยคืนแล้ว

## 4. Query หลักและ Index

เขียน Query หาหนังสือ รายการสำเนาพร้อมยืม ประวัติสมาชิก รายการเกินกำหนด และรายงานยอดยืม ทดสอบข้อมูลที่มีจำนวนและการกระจายสมจริง แล้วตรวจ EXPLAIN ก่อนเพิ่ม Index

## 5. ทดสอบความถูกต้อง

ทดสอบสองคนยืมสำเนาสุดท้ายพร้อมกัน สมาชิกใกล้เต็มโควตายืมสองเล่มพร้อมกัน คืนซ้ำ ปิดสมาชิกระหว่างยืม และวันที่ไม่ถูกต้อง ระบุสภาพข้อมูลสุดท้ายที่คาดทุกกรณี

## 6. Migration และการกู้คืน

ลองเพิ่มคอลัมน์กับข้อมูลเก่าโดยไม่ทำให้โปรแกรมเดิมพัง จากนั้นสำรองและกู้คืนไปฐานข้อมูลทดลอง ตรวจสิทธิ์ Query และ workflow สำคัญหลัง Restore

## สิ่งที่ส่งมอบ

| ชิ้นงาน | เกณฑ์ตรวจ |
|---|---|
| กฎและสมมติฐาน | ไม่มีคำกำกวมเรื่องเวลา สถานะ และขอบเขตข้อมูล |
| Schema และพจนานุกรมข้อมูล | ชื่อ ชนิด ความหมาย NULL และคีย์ชัดเจน |
| Workflow | จุดล็อก การตรวจ การ commit และ retry ชัดเจน |
| Query และ Index | มีเหตุผลจากงานจริงและแผน Query |
| กรณีทดสอบ | ครอบคลุมข้อผิดพลาดและหลาย Connection |
| แผนดูแล | Migration, Audit เท่าที่จำเป็น และผลการซ้อม Restore |

ยังไม่ต้องเพิ่ม Multi-tenant, Outbox, Partitioning หรือ Sharding จนกว่าโจทย์จะต้องใช้ อธิบายเหตุผลที่เลือกและสิ่งที่ยังไม่ทำไว้เพื่อให้ทบทวนภายหลังได้
