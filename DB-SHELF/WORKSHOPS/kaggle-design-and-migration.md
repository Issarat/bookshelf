# Workshop: Database Design และ Migration ด้วย Dataset จาก Kaggle

[สารบัญ Workshop](README.md) · [สารบัญบทเรียน](../README.md)

## เป้าหมาย

ฝึกเชื่อมการออกแบบตารางกับการย้ายข้อมูลจาก CSV การทำ Data Cleansing การตรวจความถูกต้อง และการเปลี่ยน Schema ที่มีข้อมูลอยู่แล้ว ผลงานควรเป็น Schema และขั้นตอนที่ตรวจสอบได้ ตั้งแต่ข้อมูลต้นฉบับจนถึงผลหลัง Migration

ใช้ [Brazilian E-Commerce Public Dataset by Olist บน Kaggle](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) เป็นโจทย์หลัก ระดับกลาง–สูง แนะนำบท 1–4, 7, 9–12 และ 16–19 ของ DB-SHELF สามารถลองออกแบบเองก่อนเทียบกับ [ชุด SQL และวิธีรัน](kaggle-sql/README.md) ซึ่งมีข้อมูลจำลองให้เริ่มทดลองได้

## 1. กฎธุรกิจและข้อยกเว้น

เริ่มจากลูกค้า คำสั่งซื้อ สินค้า ผู้ขาย รายการสินค้า และข้อมูลการชำระเงิน ใช้ CSV หลัก 6 ไฟล์ที่ระบุใน [คู่มือเตรียมข้อมูล](kaggle-sql/README.md) บันทึกที่มา เวอร์ชัน วันที่ดาวน์โหลด checksum และเงื่อนไขการใช้ พร้อมเก็บไฟล์ต้นฉบับแยกจากไฟล์ที่แก้เพื่อทดลอง

แยกสิ่งที่ต้นทางระบุ สิ่งที่ตรวจพบจากไฟล์ และสมมติฐานเพื่อฝึกให้ชัด ตาม Data Card ของ Olist `customer_id` ผูกกับแต่ละคำสั่งซื้อ ส่วน `customer_unique_id` ใช้ระบุลูกค้าที่กลับมาซื้อซ้ำ จึงต้องรักษาความหมายของทั้งสองรหัสไว้ ([คำอธิบายต้นทาง](https://www.kaggle.com/olistbr/brazilian-ecommerce/home/))

กำหนดวิธีจัดการค่าว่าง คีย์ซ้ำ วันที่ผิด และรายการลูกที่ไม่มีแม่ อย่าเติมสถานะจ่าย สกุลเงิน หรือ Refund ที่ไฟล์ไม่ได้ให้มาแล้วถือว่าเป็นข้อมูลจริง การไม่พบค่าซ้ำใน Dataset ก็ยังไม่พิสูจน์ว่าธุรกิจห้ามซ้ำเสมอไป

## 2. Grain และ Constraints

เขียนหนึ่งประโยคต่อหนึ่งตารางว่าหนึ่งแถวแทนอะไร แล้วออกแบบลูกค้า บริบทลูกค้าของคำสั่งซื้อ คำสั่งซื้อ สินค้า ผู้ขาย รายการสินค้า และรายการชำระเงิน โดยตรวจ Candidate Key กับไฟล์ที่ดาวน์โหลดก่อนประกาศข้อกำหนด

แยกลูกค้าตาม `customer_unique_id` ออกจากบริบทตาม `customer_id` ตรวจว่ารายการสินค้าใช้คู่รหัสคำสั่งซื้อกับลำดับรายการ และข้อมูลการจ่ายใช้คู่รหัสคำสั่งซื้อกับลำดับการจ่ายได้หรือไม่ ไม่ใช้รหัสสินค้าเพียงตัวเดียวแทนบรรทัดสินค้า หรือใช้ยอดเงินแทนตัวตนของการจ่าย

กำหนด Primary Key, Foreign Key, UNIQUE, NOT NULL และ CHECK พร้อมอธิบายความหมายของ NULL เลือก NUMERIC สำหรับจำนวนเงินและข้อความสำหรับรหัสไปรษณีย์ หากเวลาไม่มี offset ต้องกำหนดวิธีตีความก่อนแปลงเป็น TIMESTAMPTZ โดยไม่อาศัยเขตเวลาของเครื่องอย่างเงียบ ๆ

ถ้าใช้รหัสภายในใหม่ ต้องตามกลับรหัสต้นทางได้ ลองออกแบบก่อนเปิดดู [ตัวอย่าง Schema ปลายทาง](kaggle-sql/00_setup.sql)

## 3. Workflow นำเข้าและย้ายข้อมูล

แยกขั้นรับ CSV เข้า Staging ออกจากขั้นย้ายเข้าตารางใช้งาน เก็บค่าดิบและข้อมูล batch ก่อนแปลงชนิด ตรวจ header ค่าว่าง รูปแบบข้อมูล คีย์ซ้ำ และความสัมพันธ์ แล้วเก็บแถวที่ไม่ผ่านพร้อมเหตุผลให้ย้อนตรวจได้

### Data Cleansing ก่อน Validation

ใช้ลำดับ **CSV → Raw Staging → Cleansed Staging → Validation → ตารางปลายทาง → Reconciliation** สำรวจข้อมูลก่อนเลือกกฎ และแยกข้อมูลที่ถูกอยู่แล้ว ข้อมูลที่แปลงได้อย่างชัดเจน และข้อมูลที่ต้องตรวจเพิ่ม ไม่แก้ค่าดิบทับเพื่อให้ผ่าน

| สิ่งที่พบ | กฎในชุด SQL | สิ่งที่ต้องรักษา |
|---|---|---|
| ช่องว่างรอบค่า เช่น `" c1 "` | ตัดช่องว่าง ASCII รอบค่าในฟิลด์ CSV ที่กำหนด | ค่าเดิมและประวัติการแปลง; ตรวจคีย์ชนกันหลังตัด |
| ข้อความว่างหรือมีแต่ช่องว่าง | แปลงเป็น NULL แล้วตรวจว่าคอลัมน์ยอมรับหรือไม่ | ไม่เติมค่าทดแทนโดยเดา |
| จำนวนเต็มเป็น `40.0` | แปลงเป็น `40` เฉพาะเมื่อเศษเป็นศูนย์และอยู่ในช่วงชนิดข้อมูล | ไม่ปัด `40.5` เป็นจำนวนเต็ม |
| เงินเป็น `15.0` | จัดรูปแบบเป็น `15.00` เมื่อแทนค่าได้ตรง | ไม่ปัดทศนิยมเกินสองหลักหรือรับค่าติดลบ |
| รหัสไปรษณีย์ `00123` | เก็บเป็นข้อความหลังตัดช่องว่างรอบค่า | ศูนย์นำหน้าต้องไม่หาย |
| วันที่ผิด คีย์ซ้ำ หรือรหัสแม่ไม่มี | ไม่แก้เอง ให้ Validation เก็บ Reject | ค่าดิบและเหตุผลต้องตรวจย้อนหลังได้ |

ทดลอง [01_cleanse.sql](kaggle-sql/01_cleanse.sql) หลัง Load และก่อน Validate กฎรุ่น `v1` เก็บผลใน `kw_staging.cleaned_records` และบันทึกค่าก่อน/หลัง ชื่อกฎ และ record ต้นทางใน `kw_migration.cleansing_changes` โดยไม่แก้ `kw_staging.records` การตัดช่องว่างเป็นนโยบายของห้องทดลองนี้ ไม่ควรนำไปใช้กับข้อความอิสระทุกชนิดโดยไม่พิจารณาความหมาย

ชุดนี้ไม่เติมค่าเฉลี่ย ลบ Outlier เปลี่ยนตัวพิมพ์ หรือรวมลูกค้าที่ชื่อคล้ายกัน เพราะอาจเปลี่ยนข้อเท็จจริงของธุรกรรม หากต้องเพิ่มกฎ ให้ระบุเหตุผล ผู้รับผิดชอบ และวิธีตรวจผลก่อนใช้

ย้ายตารางแม่ก่อนตารางลูก ใช้ Mapping ของรหัสอย่างชัดเจน และกำหนดว่าเมื่อพบข้อผิดพลาดจะหยุดทั้ง batch หรือรับเฉพาะส่วนที่ถูกต้อง หากรับบางส่วนต้องบอกได้ว่าปลายทางยังขาดข้อมูลใด และห้ามรายงานว่าสำเร็จครบโดยไม่ตรวจ

ทำให้รันซ้ำได้โดยไม่เพิ่มข้อมูลหรือยอดซ้ำ และแยกกรณีไฟล์เดิมออกจากกรณีรหัสเดิมแต่เนื้อหาเปลี่ยน อย่าใช้ ON CONFLICT DO NOTHING เพื่อข้ามความต่างโดยไม่ตรวจสอบ

ชุด SQL ที่ให้มาใช้ snapshot คงที่: ย้ายทั้งชุดเมื่อ validation ของชั้น Cleansed ผ่าน รันซ้ำด้วยข้อมูลเดิมได้ แต่ยังเปรียบเทียบ snapshot ของค่าดิบและปฏิเสธ source ที่เปลี่ยนหลังนำเข้าสำเร็จแล้ว แม้ Cleansing จะทำให้ค่าปลายทางเท่ากัน เริ่มทดลองด้วย fixtures ก่อนใช้ฐานทดลองใหม่กับไฟล์ Kaggle ตาม [ขั้นตอนนำเข้า](kaggle-sql/README.md)

## 4. Query หลักและ Index

เขียน Query หาประวัติคำสั่งซื้อของลูกค้าคนเดิม รายการสินค้าและผู้ขาย ยอดสินค้ากับค่าขนส่งต่อคำสั่งซื้อ และยอดชำระต่อคำสั่งซื้อ พร้อม Query ตรวจคีย์ซ้ำ ค่าว่าง และรายการลูกที่หาแม่ไม่เจอ

รวมยอดรายการสินค้าและยอดชำระแยกกันก่อน JOIN เพราะทั้งสองฝั่งมีหลายแถวต่อคำสั่งซื้อ อย่าสมมติว่ายอดสินค้า ค่าขนส่ง และยอดชำระต้องเท่ากันทุกกรณีโดยไม่ตรวจความหมายต้นทาง

เลือก Index จาก Query และลำดับ Migration ที่ใช้จริง ตรวจ EXPLAIN กับข้อมูลที่มีขนาดและการกระจายใกล้เคียงงานจริง ไม่เพิ่ม Index ทุกคอลัมน์เพียงเพราะเป็นรหัส

## 5. ทดสอบความถูกต้อง

ตรวจ Mapping และค่ารายฟิลด์ รวมถึงจำนวนรายการตาม Grain และยอดต่อคำสั่งซื้อ การแยกลูกค้าออกจากบริบททำให้จำนวนแถวต่างจากต้นทางได้ จึงต้องอธิบายการเปลี่ยนจำนวน ไม่เทียบเพียงยอดแถวรวมทั้งระบบ

ทดสอบคีย์ซ้ำ รหัสลูกที่ไม่มีแม่ วันที่ผิดตามปฏิทิน เงินที่ละเอียดเกินชนิดปลายทาง และค่าว่างที่อนุญาตหรือห้ามไว้ สร้างสำเนาไฟล์สำหรับกรณีผิดโดยไม่แก้ต้นฉบับ พร้อมระบุว่า target ต้องอยู่ในสภาพใดหลังแต่ละกรณี

ตรวจเพิ่มว่า Raw ไม่เปลี่ยนหลัง Cleansing รหัสไปรษณีย์ยังมีศูนย์นำหน้า แถวก่อน/หลังเท่ากัน และทุกฟิลด์ที่เปลี่ยนมีหลักฐาน รัน Cleansing ซ้ำ batch เดิมแล้วต้องไม่เพิ่มประวัติซ้ำ หากคีย์สองค่ากลายเป็นค่าเดียวกันหลังตัดช่องว่าง ต้อง Reject ไม่เลือกทิ้งแถวใดเอง

ทดสอบไฟล์เดิมรันซ้ำ รหัสเดิมแต่ค่าต่าง และความล้มเหลวกลางขั้นตอน ตรวจว่าไม่เกิดแถวซ้ำ ไม่เขียนทับโดยไม่ตั้งใจ และไม่บันทึกว่าสำเร็จก่อนข้อมูลผ่านการตรวจ ตัวเลขรวมที่ตรงกันอย่างเดียวไม่พอ เพราะข้อผิดพลาดแต่ละรายการอาจหักล้างกัน

ใช้ [สคริปต์ Reconciliation](kaggle-sql/04_verify.sql) และ [ชุดทดสอบด้วย fixtures](kaggle-sql/test.ps1) เป็นตัวอย่าง ชุดนี้ผ่านการทดสอบบน PostgreSQL 17.2 ด้วยข้อมูลจำลอง ยังไม่ได้ตรวจไฟล์ Kaggle จริงทั้งชุด ให้ตรวจผลของเวอร์ชันที่ใช้เองด้วย

## 6. Schema Migration และการกู้คืน

ลองเปลี่ยน `orders.status` เป็น `order_status` โดยโปรแกรมเก่ายังใช้งานระหว่างเปลี่ยนผ่าน ใช้ Expand–Migrate–Contract: เพิ่มคอลัมน์ รักษาค่าสองฝั่งให้ตรง เติมข้อมูลเก่า ตรวจผล แล้วจึงลบคอลัมน์เดิมเมื่อไม่มี client ใช้แล้ว

ทดสอบ writer เก่าและใหม่ รวมถึงกรณีส่งค่าสองคอลัมน์ที่ขัดกัน การคัดลอกเพียงครั้งเดียวไม่พอหากยังมีการแก้ข้อมูล เลือกกฎว่าค่าขัดกันต้องถูกปฏิเสธหรือมีแหล่งหลักใด และทำให้การรัน Migration ซ้ำมีผลที่อธิบายได้

สำรองก่อนเปลี่ยน Schema แล้วซ้อม Restore ไปฐานทดลองแยก ตรวจ Query, Constraints และผล Reconciliation หลังคืนข้อมูล หาก Contract ลบข้อมูลไป การย้อน DDL อย่างเดียวไม่ได้กู้ค่าที่หายไปกลับมา

ลองออกแบบขั้นตอนเองก่อนเทียบกับ [Expand](kaggle-sql/05_expand.sql), [Backfill](kaggle-sql/06_backfill.sql) และ [Contract](kaggle-sql/07_contract.sql) ส่วนคำสั่งรัน เงื่อนไขการรันซ้ำ และข้อจำกัดของชุดตัวอย่างอยู่ใน [คู่มือ SQL](kaggle-sql/README.md)

## สิ่งที่ส่งมอบ

| ชิ้นงาน | เกณฑ์ตรวจ |
|---|---|
| กฎ สมมติฐาน และ Source manifest | ระบุที่มา เวอร์ชัน checksum และแยกข้อเท็จจริงจากกฎที่ตั้งเพื่อฝึก |
| Schema และพจนานุกรมข้อมูล | Grain, Keys, NULL, เวลา และ customer_id/customer_unique_id ชัดเจน |
| Workflow, Cleansing และ Mapping | กฎแปลงมีรุ่น เก็บ Raw และค่าก่อน/หลัง ลำดับย้าย Transaction วิธีรันซ้ำ และ Reject ตรวจสอบได้ |
| Query และ Index | มี Query ใช้งานและตรวจข้อมูล พร้อมเหตุผลจากแผน Query |
| กรณีทดสอบและ Reconciliation | ครอบคลุมข้อมูลผิด ข้อมูลขาด รันซ้ำ และยอดรายคำสั่งซื้อ |
| แผน Migration และการกู้คืน | ทดสอบ writer เก่า/ใหม่ ผลก่อนและหลัง Contract และซ้อม Restore |

เริ่มจากไฟล์เวอร์ชันคงที่และฐานทดลองที่ไม่มี writer อื่นก่อน ยังไม่ต้องเพิ่ม CDC หรือการย้ายแบบไม่หยุดเขียนจนกว่าโจทย์จะต้องใช้ หากต่อยอดให้มีการเขียนพร้อมกัน ต้องกำหนดจุดตัดและการตามข้อมูลเปลี่ยนอย่างถูกต้อง ไม่ใช้ MAX(id) แทนลำดับ COMMIT โดยไม่มีหลักประกัน
