# 4. Normalization และ Snapshot

[สารบัญ](README.md) · [บทก่อนหน้า](keys-and-constraints.md) · [บทถัดไป](practical-design.md)

## ปัญหาจากข้อมูลซ้ำ

ถ้า `books` เก็บชื่อและที่อยู่สำนักพิมพ์ทุกเล่ม เมื่อสำนักพิมพ์ย้ายต้องแก้หลายแถว หากแก้ไม่ครบจะได้ข้อมูลขัดกัน เรียกว่า Update Anomaly

แยกเป็น:

```text
publishers(publisher_id, name, address)
books(book_id, title, publisher_id)
```

ค่าเหมือนกันไม่ได้แปลว่าต้องแยกตารางเสมอ เช่น หนังสือหลายเล่มมี 200 หน้า ไม่จำเป็นต้องสร้างตารางจำนวนหน้า

## Functional Dependency

`member_id → member_name` หมายถึง ในข้อมูลที่ถูกต้อง ณ สถานะหนึ่ง รหัสสมาชิกกำหนดชื่อได้หนึ่งค่า ไม่ได้หมายความว่าสมาชิกเปลี่ยนชื่อไม่ได้

| ระดับ | แนวคิด |
|---|---|
| 1NF | ไม่มีชุดคอลัมน์ซ้ำอย่าง `author1`, `author2`; แต่ละช่องมีค่าหนึ่งค่าตามโดเมนที่กำหนด |
| 2NF | ผ่าน 1NF และคอลัมน์ที่ไม่อยู่ใน Candidate Key ไม่ขึ้นกับเพียงบางส่วนของ Candidate Key |
| 3NF | สำหรับ Dependency ที่ไม่เป็นเรื่องซ้ำในตัวเอง ตัวกำหนดต้องเป็น Superkey หรือคอลัมน์ที่ถูกกำหนดเป็นส่วนหนึ่งของ Candidate Key |

คำอธิบายใช้งานทั่วไปของ 3NF คือหลีกเลี่ยงการให้ข้อมูลนอกคีย์ขึ้นต่อกันเป็นทอด ๆ แต่เกณฑ์อย่างเป็นทางการข้างต้นครอบคลุมกรณีหลาย Candidate Key ด้วย

### Partial Dependency

ใน `order_items` ที่ใช้ `(order_id, product_id)` เป็นคีย์ แต่ `ordered_at` ขึ้นกับ `order_id` อย่างเดียว ควรย้ายวันสั่งซื้อไป `orders`

### Transitive Dependency

```text
order_id → member_id → member_name
```

ถ้าต้องการชื่อปัจจุบัน ให้เก็บชื่อใน `members` และ JOIN ไม่ต้องแก้ทุกคำสั่งซื้อเมื่อเปลี่ยนชื่อ เช่นเดียวกับการแยก `departments` ออกจาก `employees`

## Snapshot เป็นคนละข้อเท็จจริง

ชื่อปัจจุบันกับชื่อ ณ วันที่ซื้อมีความหมายต่างกัน จึงเก็บชื่อสินค้า ราคา และที่อยู่จัดส่ง ณ วันยืนยันคำสั่งซื้อไว้ได้ แม้มีข้อมูลปัจจุบันในตารางต้นทาง

| ข้อมูล | แนวทาง |
|---|---|
| ชื่อสมาชิกปัจจุบัน | อ้าง Foreign Key แล้ว JOIN |
| ราคาที่ตกลงซื้อ | Snapshot ใน `order_items.unit_price` |
| กำหนดคืนของการยืมครั้งนั้น | เก็บ `loans.due_at` |
| ยอดสุทธิที่ยืนยันแล้ว | เก็บตามกฎการคำนวณและการปัดเศษ ณ เวลานั้น |

## ค่าที่คำนวณได้

ความพร้อมให้ยืมหาจากการไม่มีรายการยืมค้างได้:

```sql
SELECT bc.copy_id,
       NOT EXISTS (
           SELECT 1 FROM loans l
           WHERE l.copy_id = bc.copy_id
             AND l.returned_at IS NULL
       ) AS has_no_active_loan
FROM book_copies bc;
```

แต่พร้อมให้ยืมจริงยังต้องตรวจสภาพ เช่น ไม่ชำรุดหรือสูญหาย การเก็บ `is_available` ซ้ำต้องมีเหตุผลและกลไกรักษาความสอดคล้อง

## JSONB, BYTEA และ Hash

คอลัมน์ปกติเหมาะกับข้อมูลหลักที่ต้องตรวจชนิด เชื่อมตาราง และบังคับกฎ ส่วน `JSONB` เหมาะกับรายละเอียดเสริมที่โครงสร้างแตกต่างกัน โดยต้องเพิ่ม validation ตามต้องการ

รายชื่อผู้เขียนควรใช้ `authors` และ `book_authors` เพื่อค้นหา เชื่อมโยง และกำหนดลำดับ ไม่ควรเก็บเป็นก้อนไบนารี (`BYTEA`) แล้ว Hash เพื่อแทนความสัมพันธ์ Hash ช่วยตรวจเนื้อหา แต่ไม่ใช่ตัวตนของบุคคล คนต่างกันอาจชื่อเหมือนกัน และคนเดิมเปลี่ยนชื่อได้
