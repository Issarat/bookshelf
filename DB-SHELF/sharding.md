# 22. Sharding และการกระจายฐานข้อมูล

[สารบัญ](README.md) · [บทก่อนหน้า](replication.md) · [บทถัดไป](data-warehouse.md)

## แยกความหมาย

| แนวคิด | จุดหลัก |
|---|---|
| Partitioning | แบ่งตารางเป็นส่วนย่อย ไม่ได้แปลว่ากระจายหลายเครื่อง |
| Replication | สำเนาข้อมูลไปปลายทาง |
| Sharding | แบ่งคนละชุดข้อมูลไปฐานข้อมูลหรือโหนดต่างกัน |

Sharding เป็นการตัดสินใจด้านสถาปัตยกรรม ต้องเลือกผลิตภัณฑ์ กลไก routing และการปฏิบัติการ ไม่ได้เกิดขึ้นเพียงสร้าง partition ใน PostgreSQL

## เลือก Shard Key จากธุรกรรม

ระบบหลายบริษัทอาจแบ่งตาม tenant_id เพื่อให้คำสั่งซื้อและรายการของบริษัทเดียวอยู่ด้วยกัน แต่บริษัทขนาดใหญ่หนึ่งรายอาจทำให้ shard ร้อนกว่ารายอื่น

พิจารณาการกระจายโหลด การเติบโต การย้ายข้อมูล และ Query ข้ามขอบเขต หากแบ่งด้วย hash อาจกระจายได้ดีแต่ Query ตามช่วงต้องกระจายหลาย shard หากแบ่งตามช่วงอาจเกิด hotspot ต้องประเมินตามข้อมูลจริง

## สิ่งที่ซับซ้อนขึ้น

- JOIN และรายงานข้าม shard ต้องรวมผลหลายที่
- Transaction และ UNIQUE ข้าม shard ต้องมีกลไกเพิ่มเติมตามระบบที่ใช้
- ต้องจัดการรหัสไม่ชน routing การย้าย shard และการ retry
- Backup/Restore ต้องรักษาความสอดคล้องของหลายส่วนตามเป้าหมาย
- การตรวจปัญหาและการเปลี่ยน Schema ต้องทำหลายปลายทาง

UUID ช่วยเรื่องการสร้างรหัสตามวิธีที่เลือก แต่ไม่ทำให้ Foreign Key หรือกฎยอดรวมข้าม shard ถูกบังคับโดยอัตโนมัติ

## เมื่อใดค่อยพิจารณา

มีข้อจำกัดที่วัดได้ซึ่งแก้ด้วย Query, Index, ขนาดเครื่อง การเก็บข้อมูลเก่า หรือการแยกงานอ่านไม่ได้อย่างเหมาะสม และทีมรับต้นทุนดูแลไหว ไม่เลือกเพียงเพราะคาดว่าวันหนึ่งระบบจะใหญ่

## แบบฝึกหัด

ถ้าแบ่งด้วย tenant_id แต่รายงานหลักต้องสรุปยอดทุกบริษัททุกชั่วโมง จะจัดการการรวมข้อมูล ความล่าช้า และการตรวจยอดตรงกันอย่างไร? เขียนสมมติฐานก่อนเลือกเครื่องมือ
