# 8. เลือกใช้ SQL กับ NoSQL อย่างไร

[สารบัญ](README.md) · [บทก่อนหน้า](data-governance.md) · [บทถัดไป](transactions-and-concurrency.md)

## เริ่มจากงานที่ต้องทำ

เลือกจากรูปแบบข้อมูล กฎที่ต้องรักษา วิธีอ่านเขียน และความสามารถของทีม ไม่ใช่ตัดสินจากจำนวนข้อมูลหรือความนิยมอย่างเดียว

SQL เป็นภาษาสำหรับจัดการข้อมูล ในบทนี้ใช้คำว่า SQL database หมายถึงฐานข้อมูลเชิงสัมพันธ์ เช่น PostgreSQL ส่วน NoSQL เป็นชื่อกลุ่มฐานข้อมูลหลายรูปแบบ จึงไม่ควรเหมารวมว่าทุกตัวมีความสามารถหรือข้อจำกัดเหมือนกัน

## ตารางเปรียบเทียบ

| ประเด็น | ฐานข้อมูลเชิงสัมพันธ์ | ฐานข้อมูล NoSQL |
|---|---|---|
| รูปแบบข้อมูล | ตารางและความสัมพันธ์ ใช้ JSON ร่วมได้ในบางระบบ | ขึ้นกับประเภท เช่น เอกสาร Key-value Graph หรือ Wide-column |
| การรักษากฎ | ใช้คีย์ Foreign Key, UNIQUE, CHECK และ Transaction | ต้องตรวจความสามารถของผลิตภัณฑ์ บางกฎอาจต้องดูแลในโปรแกรม |
| การอ่านข้อมูล | JOIN และ Query ได้หลายรูปแบบ | มักออกแบบตามวิธีเข้าถึงเฉพาะ เช่น อ่านเอกสารหรือค้นหาด้วย Key |
| Schema | มีโครงสร้างที่ฐานข้อมูลบังคับตามที่ประกาศ | อาจยืดหยุ่นกว่า แต่โปรแกรมยังต้องมีข้อตกลงเรื่องโครงสร้าง |
| Transaction | เหมาะกับงานที่ต้องรักษาความสอดคล้องหลายแถวหรือตาราง | บางตัวรองรับหลายเอกสาร ต้องตรวจขอบเขตและต้นทุน |
| การขยายระบบ | ขึ้นกับระบบและสถาปัตยกรรม ไม่ได้จำกัดว่าต้องขยายเครื่องเดียว | บางประเภทออกแบบเพื่อกระจายงาน แต่ไม่ได้ง่ายหรือเหมาะทุกกรณี |

ตารางนี้เป็นแนวทางตั้งคำถาม ไม่ใช่ข้อรับรองว่าทุกผลิตภัณฑ์มีพฤติกรรมเหมือนกัน ต้องตรวจรุ่น การตั้งค่า และข้อจำกัดของระบบที่จะใช้จริง

## เมื่อใดเริ่มจาก SQL

SQL เหมาะเป็นจุดเริ่มต้นเมื่อข้อมูลสัมพันธ์กันมาก ต้องรักษากฎข้ามรายการ และต้องค้นหาหรือทำรายงานหลายรูปแบบ เช่น:

- ระบบยืมหนังสือ: สมาชิก สำเนา และประวัติการยืม
- ระบบสั่งซื้อ: คำสั่งซื้อ รายการสินค้า การจ่ายเงิน และการคืนเงิน
- ระบบลงทะเบียน: นักเรียน วิชา เทอม และจำนวนที่นั่ง

ตัวอย่างกฎที่เราเรียนมา ได้แก่ ห้ามยืมสำเนาเดียวกันค้างพร้อมกัน การลงทะเบียนต้องอ้างถึงวิชาที่เปิดสอนจริง และการจ่ายต้องใช้สกุลเงินเดียวกับคำสั่งซื้อ PostgreSQL มี Constraints และ Transaction ที่นำมาใช้รักษากฎเหล่านี้ได้

## NoSQL มีหลายประเภท

| ประเภท | ตัวอย่าง | ลักษณะงานที่นำมาพิจารณา |
|---|---|---|
| Document | MongoDB | ข้อมูลเป็นเอกสารที่มักอ่านเขียนร่วมกัน และรายละเอียดต่างกันแต่ละประเภท |
| Key-value | Redis | เข้าถึงข้อมูลด้วย Key เป็นหลัก เช่น Cache หรือ Session โดยกำหนดเรื่องอายุและความทนทานของข้อมูลให้เหมาะสม |
| Graph | Neo4j | ความสัมพันธ์หลายทอดเป็นงานหลัก เช่น สำรวจเส้นทางหรือเครือข่ายความสัมพันธ์ |
| Wide-column | Apache Cassandra | รูปแบบอ่านเขียนที่กำหนดชัด และต้องออกแบบการกระจายข้อมูลตามรูปแบบการเข้าถึง |

การมีข้อมูลเป็นกราฟไม่ได้แปลว่าต้องใช้ Graph database เสมอ เช่น หมวดหมู่เล็ก ๆ ยังใช้ parent_id ใน PostgreSQL ได้ เช่นเดียวกับเอกสารยืดหยุ่นที่อาจใช้ JSONB ได้เพียงพอ

## ออกแบบตามขอบเขตที่อ่านและแก้พร้อมกัน

Document database อาจเก็บรายการสินค้าของคำสั่งซื้อไว้ในเอกสารคำสั่งซื้อ เมื่อมักอ่านรายละเอียดทั้งชุดพร้อมกัน การเก็บร่วมกันอาจตรงกับรูปแบบใช้งาน

แต่ต้องถามเพิ่มว่า:

1. รายการย่อยเติบโตได้มากแค่ไหน และมีข้อจำกัดขนาดเอกสารหรือไม่?
2. ต้องแก้รายการย่อยแยกกันหรือมีผู้ใช้เขียนพร้อมกันมากไหม?
3. ต้องค้นหารายการสินค้าข้ามคำสั่งซื้อบ่อยหรือไม่?
4. ข้อมูลที่คัดลอกไปหลายเอกสารต้องตรงกันทันทีหรือยอมให้ล่าช้าได้?
5. Transaction และ Index ของผลิตภัณฑ์รองรับงานนี้อย่างไร?

การลด JOIN โดยเก็บข้อมูลซ้ำเป็นการแลกต้นทุนอ่านกับต้นทุนอัปเดต ไม่ได้ทำให้ปัญหาความสอดคล้องหายไป

## PostgreSQL กับ JSONB

ไม่จำเป็นต้องเปลี่ยนฐานข้อมูลเพียงเพราะรายละเอียดสินค้าแตกต่างกัน:

```sql
CREATE TABLE products (
    product_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb,
    CHECK (jsonb_typeof(attributes) = 'object')
);
```

ข้อมูลหลักที่ต้องบังคับกฎเก็บเป็นคอลัมน์ ส่วน attributes เก็บรายละเอียดเสริม เช่น ภาษา จำนวนหน้า หรือสี CHECK ในตัวอย่างบังคับเพียงว่าเป็น object ไม่ได้ตรวจชื่อฟิลด์หรือชนิดค่าภายในทั้งหมด

การที่ PostgreSQL เก็บ JSON ได้ ไม่ได้แปลว่าควรย้ายทุกอย่างไป JSONB โดยเฉพาะ Foreign Key และข้อมูลที่ต้องค้นหา เชื่อมโยง หรือบังคับกฎเป็นประจำ

## ใช้ร่วมกันได้ แต่มีต้นทุน

ตัวอย่างหนึ่งคือ PostgreSQL เป็นแหล่งข้อมูลหลัก และ Redis เก็บ Cache ของข้อมูลที่อ่านบ่อย ต้องกำหนดว่า Cache หมดอายุเมื่อไร อัปเดตอย่างไร และยอมให้ข้อมูลเก่าได้นานแค่ไหน

การเพิ่มฐานข้อมูลอีกตัวเพิ่มงานสำรองข้อมูล เฝ้าระวัง จัดการสิทธิ์ และรับมือความผิดพลาด หาก Query ใน PostgreSQL ยังตอบโจทย์ได้ การเพิ่มระบบใหม่อาจเป็น Overengineering

## ความเข้าใจผิดที่พบบ่อย

- NoSQL ไม่ได้เร็วกว่า SQL เสมอ ต้องวัดด้วย Query และข้อมูลใกล้เคียงของจริง
- NoSQL ไม่ได้แปลว่าไม่มี Schema โปรแกรมยังต้องเข้าใจชนิดและความหมายของข้อมูล
- NoSQL บางตัวมี Transaction แต่ต้องตรวจว่าครอบคลุมงานที่ต้องการหรือไม่
- SQL รองรับข้อมูลจำนวนมากได้ การขยายระบบต้องพิจารณาทั้งการออกแบบ Index, Query และสถาปัตยกรรม
- ความยืดหยุ่นไม่ทำให้การเปลี่ยนโครงสร้างข้อมูลฟรี ข้อมูลเก่าและโปรแกรมหลายเวอร์ชันยังต้องเข้ากันได้

## ขั้นตอนตัดสินใจก่อนเลือก

1. เขียน Query สำคัญอย่างน้อย 5 รายการ รวมรายงานที่ต้องใช้
2. เขียนกฎที่ห้ามผิด และระบุขอบเขตของ Transaction
3. ประเมินปริมาณข้อมูล อัตราอ่านเขียน ขนาดแต่ละรายการ และเวลาตอบสนองที่ต้องการ
4. ระบุความสดของข้อมูลที่ยอมรับได้ โดยเฉพาะข้อมูลที่ทำสำเนาหรือกระจายข้ามระบบ
5. ประเมินทักษะทีม การสำรองและกู้คืน ค่าใช้จ่าย และภาระดูแล
6. ทดลองด้วยข้อมูลใกล้เคียงจริงเมื่อมีข้อกังวลด้านประสิทธิภาพ ไม่ตัดสินจากคำกล่าวทั่วไป

สำหรับระบบตัวอย่างใน DB-SHELF เริ่มจาก PostgreSQL สอดคล้องกับความสัมพันธ์และกฎที่กำหนดไว้ แล้วพิจารณาฐานข้อมูลเฉพาะทางเมื่อมีความต้องการชัดเจนและผลวัดรองรับ

## แบบฝึกหัด

ระบบขายหนังสือต้องเก็บคำสั่งซื้อและการชำระเงิน มีรายละเอียดหนังสือแตกต่างกัน และมีหน้ารายการขายดีที่อ่านบ่อย คุณจะเริ่มด้วยฐานข้อมูลอะไร และมีหลักฐานอะไรที่ควรตรวจ ก่อนเพิ่ม Cache หรือฐานข้อมูลอีกชนิด?

แนวคำตอบ: เริ่มด้วย PostgreSQL ใช้คอลัมน์และตารางสัมพันธ์สำหรับข้อมูลธุรกรรม ใช้ JSONB เฉพาะรายละเอียดที่เหมาะสม ตรวจ Query, Index, ปริมาณงาน และความสดของรายงานก่อนเพิ่มระบบอื่น
