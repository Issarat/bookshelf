# 21. Replication และความพร้อมใช้งาน

[สารบัญ](README.md) · [บทก่อนหน้า](partitioning.md) · [บทถัดไป](sharding.md)

## Replica แก้ปัญหาอะไร

Replica เก็บสำเนาที่ติดตามการเปลี่ยนแปลง อาจใช้เตรียมเครื่องรับช่วงเมื่อ primary ล้ม หรือแบ่งงานอ่านเมื่อออกแบบเส้นทางและความสดของข้อมูลแล้ว ไม่ได้ช่วยกระจายงานเขียนทุกแบบโดยอัตโนมัติ

| รูปแบบ | ข้อพิจารณา |
|---|---|
| Asynchronous | ลดการรอยืนยันจากปลายทาง แต่ Replica อาจตามไม่ทันและมีความเสี่ยงเสียรายการที่ยังไม่ส่งเมื่อ primary เสีย |
| Synchronous | รอการยืนยันตามการตั้งค่า แลกกับ latency และความพร้อมเมื่อปลายทางมีปัญหา |

ความหมายของการยืนยันขึ้นกับการตั้งค่า อย่าเหมารวมว่าทุก synchronous mode ทำให้ SELECT บน Replica เห็นข้อมูลทันที

## Read-after-write

หลังสร้างคำสั่งซื้อที่ primary ถ้าอ่านจาก Replica ที่ยังตามไม่ทัน อาจดูเหมือนข้อมูลหาย ทางเลือกคืออ่าน primary สำหรับงานที่ต้องเห็นผลทันที หรือมีกลไกรอ/เลือกเส้นทางตามความต้องการ ไม่ใช้เวลาหน่วงคงที่แล้วรับรองว่าจะทันเสมอ

รายงานที่ยอมให้ล่าช้าได้เหมาะกับเส้นทางอ่าน Replica มากกว่าการตรวจยอดก่อนทำธุรกรรมสำคัญ

## Failover เป็นกระบวนการ

กำหนดวิธีตรวจความเสียหาย เลือกเครื่องรับช่วง เปลี่ยนการเชื่อมต่อ และป้องกันเครื่องเก่ากลับมารับเขียนพร้อมกันโดยไม่ได้จัดการ บทเรียนนี้ไม่ใช่ขั้นตอนตั้งค่า failover สำเร็จรูป

ทดสอบแอปเชื่อมใหม่ Transaction ที่ไม่ทราบผล และ retry แบบ idempotent เฝ้าระวัง lag และพื้นที่ WAL ที่ค้างเพราะ Replica หรือ replication slot

Replica ไม่แทน Backup: การลบผิดหรือแก้ข้อมูลผิดอาจถูกส่งต่อ ต้องมีการกู้ย้อนหลังตามเป้าหมายแยกต่างหาก
