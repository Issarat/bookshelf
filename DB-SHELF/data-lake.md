# 24. Data Lake — เก็บข้อมูลหลายรูปแบบเพื่อใช้ต่อ

[สารบัญ](README.md) · [บทก่อนหน้า](data-warehouse.md) · [บทถัดไป](big-data.md)

## Data Lake คืออะไร

Data Lake เป็นแนวทางเก็บข้อมูลจากหลายแหล่งและหลายรูปแบบ ทั้งข้อมูลตาราง JSON, Log หรือไฟล์อื่น เพื่อให้เลือกประมวลผลและนำไปใช้ต่อได้ มักใช้พื้นที่จัดเก็บที่ขยายได้ เช่น Object Storage ร่วมกับเครื่องมือประมวลผลและ Metadata ([AWS: Data Lake](https://aws.amazon.com/what-is/data-lake/))

การวาง CSV ในโฟลเดอร์หนึ่งช่วยฝึกแนวคิดได้ แต่ระบบใช้งานจริงยังต้องมี Catalog, สิทธิ์ คุณภาพ Lineage และการจัดการเวอร์ชัน ไม่ใช่เพียงโยนไฟล์ลงพื้นที่ส่วนกลาง

## ต่างจาก Warehouse และทำงานร่วมกันอย่างไร

| ประเด็น | Data Lake | Data Warehouse |
|---|---|---|
| จุดเน้น | รองรับข้อมูลและการใช้งานหลากหลาย | ชุดข้อมูลพร้อมวิเคราะห์ตามนิยามที่กำหนด |
| ผู้ใช้งานตัวอย่าง | วิศวกรข้อมูล นักวิเคราะห์ และทีม ML | ทีม BI นักวิเคราะห์ และผู้ใช้รายงาน |
| โครงสร้าง | มีได้ทั้ง Raw และข้อมูลที่จัดรูปแบบแล้ว | มักมีแบบจำลองที่เหมาะกับรายงาน |
| ความสัมพันธ์ | เป็นแหล่งเตรียมข้อมูลให้ Warehouse ได้ | รับข้อมูลจาก Lake หรือระบบต้นทางโดยตรงได้ |

Schema-on-read กับ Schema-on-write เป็นแนวคิดช่วยอธิบาย ไม่ใช่เส้นแบ่งตายตัว Lake มีข้อมูลที่บังคับ Schema ได้ และ Warehouse อาจรองรับข้อมูลกึ่งโครงสร้างได้เช่นกัน

## จัดชั้น Raw → Cleansed → Curated

| ชั้น | หน้าที่ | ตัวอย่างจาก Olist |
|---|---|---|
| Raw | เก็บข้อมูลที่รับมาและที่มาเพื่อย้อนตรวจ | CSV เดิม พร้อม checksum/เวอร์ชัน |
| Cleansed | ใช้กฎแปลงที่ระบุไว้ ตรวจชนิดและคุณภาพ | ตัดช่องว่างตามกฎ รักษารหัสไปรษณีย์ แยก Reject |
| Curated | จัดเป็นข้อมูลพร้อมใช้ตามโจทย์ | ยอดต่อคำสั่งซื้อ หรือข้อมูลสำหรับ Fact/Dimension |

บางระบบเรียก Bronze/Silver/Gold แต่ชื่อไม่ได้รับรองคุณภาพ ต้องมีเกณฑ์ผ่านและผู้รับผิดชอบ ไม่จำเป็นต้องสร้างทุกชั้นให้ครบเหมือนกันทุกโครงการ

Raw ที่รักษาต้นฉบับไม่ได้แปลว่าห้ามมีนโยบายลบ เก็บข้อมูลเท่าที่จำเป็นตามสิทธิ์และอายุที่กำหนด รวมถึงเวอร์ชันไฟล์และ Backup

## รูปแบบไฟล์กับ Table Format

CSV อ่านง่ายแต่ไม่มีชนิดข้อมูลครบในตัว ส่วน **Parquet** เป็นรูปแบบไฟล์แบบคอลัมน์ที่ออกแบบสำหรับข้อมูลเชิงตาราง ช่วยงานอ่านบางคอลัมน์และรองรับการบีบอัดตามโครงสร้าง ไม่ได้ทำให้ทุก Query เร็วโดยอัตโนมัติ ([Apache Parquet](https://parquet.apache.org/docs/overview/))

**Table Format** อย่าง Apache Iceberg จัดการ Metadata ของตารางที่ครอบคลุมหลายไฟล์ เช่น snapshot และการเปลี่ยน Schema ตามความสามารถที่รองรับ ไม่ใช่ไฟล์รูปแบบเดียวกับ Parquet และยังต้องมี engine/catalog ที่ใช้งานร่วมกัน ([Apache Iceberg](https://iceberg.apache.org/docs/latest/))

คำว่า **Lakehouse** มักใช้กับสถาปัตยกรรมที่เพิ่มการจัดการตารางและความสามารถวิเคราะห์บนพื้นที่แบบ Lake ต้องตรวจคุณสมบัติจริงของชุดเครื่องมือ ไม่ตีความว่ารองรับ Transaction หรือ Constraints แบบ PostgreSQL ทั้งหมด

## Metadata และข้อผิดพลาดที่พบบ่อย

ต้องรู้ว่าไฟล์ใดอยู่ใน batch ไหน ข้อมูลถึงเวลาใด กฎแปลงเวอร์ชันอะไร และใครใช้ได้ ไฟล์เล็กจำนวนมากอาจเพิ่มต้นทุนอ่าน Metadata และเปิดไฟล์ ส่วน partition ที่ละเอียดเกินไปอาจยิ่งเพิ่มปัญหา

ไม่ใช้ชื่อไฟล์หรือตำแหน่งโฟลเดอร์แทนสัญญาว่าข้อมูลครบ ต้องมี manifest/checkpoint และตรวจการรับซ้ำ ข้อมูลมาช้า และ Schema ที่เปลี่ยน

หากปล่อยข้อมูลไม่มีเจ้าของ ไม่มี Catalog และไม่รู้ว่าใช้ได้หรือไม่ Lake จะกลายเป็นพื้นที่ที่หาและเชื่อถือข้อมูลได้ยาก แม้จะมีไฟล์ครบมากก็ตาม

## เชื่อมกับ Workshop Kaggle

Raw/Cleansed Staging ใน PostgreSQL เป็นตัวอย่างการแยกชั้นและรักษาประวัติการแปลง แต่ไม่ได้ทำให้ Workshop กลายเป็น Data Lake ที่กระจายหลายระบบทันที

เริ่มฝึกบนเครื่องโดยจัด Raw CSV, manifest, กฎ Cleansing และชุด Curated ให้ตรวจย้อนกลับได้ก่อน ยังไม่จำเป็นต้องซื้อบริการ Cloud เพื่อเข้าใจแนวคิดนี้

## แบบฝึกหัด

ออกแบบการจัดเก็บ Olist สองเวอร์ชันให้ไม่เขียนทับกัน ระบุ Catalog, checksum, สิทธิ์เข้าถึง กฎเก็บรักษา และวิธีเลือก Curated ชุดที่ผ่านตรวจแล้ว หากชุดใหม่ผิด ต้องย้อนใช้ชุดก่อนหน้าอย่างไร?
