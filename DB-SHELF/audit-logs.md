# 15. Audit Log และประวัติทางธุรกิจ

[สารบัญ](README.md) · [บทก่อนหน้า](orders-payments-and-events.md) · [บทถัดไป](security-views-and-migrations.md)

## เก็บเพื่อให้ตอบคำถามอะไร

| ข้อมูล | คำถาม |
|---|---|
| ประวัติธุรกิจ เช่น refunds | เคยคืนเงินจริงเท่าไร และเพราะอะไร |
| Audit Log | ใครแก้ข้อมูลอะไร จากค่าใดเป็นค่าใด เมื่อไร |
| Operational Log | คำขอไหนล้มเหลว ใช้เวลานานเท่าไร |

Audit ไม่แทนตารางธุรกรรม และ Log สำหรับ debug ไม่ควรเป็นแหล่งประวัติธุรกิจหลัก

## โครงสร้างตัวอย่าง

```sql
CREATE TABLE audit_events (
    audit_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    actor_id TEXT,
    request_id TEXT,
    entity_type TEXT NOT NULL,
    entity_key TEXT NOT NULL,
    action TEXT NOT NULL,
    old_values JSONB,
    new_values JSONB
);
```

entity_key แบบข้อความเป็นการแลกความยืดหยุ่นกับการตรวจชนิด ไม่ได้มี Foreign Key ที่ตรวจว่ารายการต้นทางมีอยู่ และอาจตั้งใจเก็บต่อหลังลบต้นทาง

## เลือกจุดบันทึก

- ในโปรแกรม: รู้เจตนาธุรกิจและผู้ใช้ แต่ต้องครอบคลุมทุกเส้นทาง
- ใน Trigger: ครอบคลุมการเปลี่ยนแถวโดยตรง แต่ต้องส่งบริบทผู้ใช้จริงอย่างเชื่อถือได้ บัญชีเชื่อมต่ออาจเป็นบัญชีกลาง

ถ้าบันทึกการแก้ที่สำเร็จ ควรอยู่ Transaction เดียวกับข้อมูล เมื่อ ROLLBACK Audit นั้นก็ถูกยกเลิกด้วย การบันทึกความพยายามที่ล้มเหลวจึงต้องมีกลไกอื่นที่เหมาะสม

## ความน่าเชื่อถือและข้อมูลละเอียดอ่อน

จำกัดสิทธิ์แก้หรือลบ Audit และกำหนดการเก็บรักษา ไม่ใส่รหัสผ่าน token หรือข้อมูลละเอียดอ่อนทั้งก้อนโดยไม่จำเป็น การมีตาราง append-only ผ่านสิทธิ์แอปไม่ได้รับรองว่าผู้ดูแลฐานข้อมูลจะแก้ไม่ได้ หากต้องตรวจการดัดแปลงต้องออกแบบเพิ่มเติม

## แบบฝึกหัด

ผู้ดูแลเปลี่ยนที่อยู่สมาชิก แล้วมีคำขอแก้อีกครั้งที่ถูกปฏิเสธ คุณต้องการเก็บทั้งสองเหตุการณ์ที่ไหน และแสดงตัวตนผู้แก้จากแหล่งใด?
