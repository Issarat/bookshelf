# 25. Big Data — เมื่อขนาด ความเร็ว และความหลากหลายเป็นโจทย์

[สารบัญ](README.md) · [บทก่อนหน้า](data-lake.md) · [บทถัดไป](data-center.md)

## Big Data คืออะไร

Big Data อธิบายโจทย์ข้อมูลที่ปริมาณ ความเร็วในการเกิด หรือความหลากหลายทำให้วิธีเดิมตอบข้อกำหนดได้ยาก ต้องพิจารณาทั้งการรับ เก็บ ประมวลผล และใช้งาน แนวคิดที่มักใช้คือ Volume, Velocity และ Variety หรือ 3V ([AWS: Big Data](https://aws.amazon.com/what-is/big-data/))

ไม่มีจำนวนแถวเดียวที่ทำให้ทุกระบบกลายเป็น Big Data งานหนึ่งอาจมีปัญหาจากข้อมูลเข้าต่อเนื่องและต้องตอบเร็ว ส่วนอีกงานมีข้อมูลสะสมมากแต่ยอมประมวลผลรายวันได้

## 3V และคุณค่าที่ต้องได้

| มิติ | คำถาม | ตัวอย่างโจทย์ที่ตั้งเพื่อฝึก |
|---|---|---|
| Volume | เก็บและอ่านมากแค่ไหน? | เก็บประวัติเหตุการณ์หลายปี |
| Velocity | ข้อมูลเข้ารวดเร็วและต้องใช้ผลเร็วแค่ไหน? | ต้องแจ้งเตือนเหตุผิดปกติภายในเวลาที่กำหนด |
| Variety | มีรูปแบบและแหล่งข้อมูลอะไรบ้าง? | ตารางธุรกรรม Log, JSON และไฟล์ภาพ |

บางคำอธิบายเพิ่ม Veracity และ Value เพื่อเน้นความน่าเชื่อถือและประโยชน์ แต่จำนวน V ไม่ใช่เกณฑ์เลือกเครื่องมือ ต้องระบุคุณภาพและผลที่งานต้องการด้วย

## ไม่ใช่ชื่อฐานข้อมูลหรือคำแทน NoSQL

Big Data เป็นลักษณะปัญหา ส่วน SQL เป็นภาษาและแนวทางฐานข้อมูลกลุ่มหนึ่ง งานข้อมูลขนาดใหญ่ยังใช้ SQL ได้ และการใช้ NoSQL ไม่ได้ทำให้งานนั้นเป็น Big Data โดยอัตโนมัติ

Warehouse หรือ Lake อาจเป็นส่วนหนึ่งของสถาปัตยกรรม Big Data แต่ไม่จำเป็นต้องมีครบทั้งหมด เช่น รายงานจากระบบเล็กก็ใช้ Warehouse ได้โดยไม่ต้องกระจายงานหลายโหนด

## Batch กับ Streaming

| แบบ | ลักษณะ | สิ่งที่ต้องกำหนด |
|---|---|---|
| Batch | ประมวลผลข้อมูลเป็นชุด | ขอบเขตชุด เวลาเสร็จ รันซ้ำ และความครบ |
| Streaming | ประมวลผลข้อมูลต่อเนื่อง | เวลาเหตุการณ์ ข้อมูลมาช้า ข้อมูลซ้ำ และช่วงสรุปผล |

เวลาเกิดเหตุการณ์กับเวลาที่ระบบรับอาจไม่ตรงกัน รายงานที่สรุปทุกนาทีต้องระบุว่าจะปรับยอดเมื่อข้อมูลมาช้าหรือปิดช่วงเมื่อไร เช่นเดียวกับเรื่อง checkpoint และ idempotency ที่เรียนในระบบ Event

## Distributed Processing และต้นทุนที่เพิ่มขึ้น

การแบ่งข้อมูลให้หลายเครื่องทำงานช่วยบางงานได้ แต่เพิ่มการส่งข้อมูลผ่านเครือข่าย การจัดการความล้มเหลว และการรวมผล ถ้าต้องย้ายข้อมูลข้ามเครื่องเพื่อ JOIN/GROUP BY มาก อาจเสียเวลาไปกับการกระจายใหม่หรือ Shuffle

คีย์ที่มีข้อมูลมากผิดสัดส่วนทำให้เกิด Skew: เครื่องหนึ่งทำงานหนักขณะที่เครื่องอื่นว่าง จึงต้องดูการกระจายข้อมูล ไม่ใช่เพิ่มจำนวนเครื่องแล้วคาดว่าจะเร็วตามสัดส่วน

การ retry ต้องไม่ทำยอดซ้ำ และการประมวลผลบางส่วนสำเร็จต้องไม่ถูกเผยแพร่เป็นผลครบ ควรกำหนดวิธี commit ผลงานทั้งชุดหรือวิธีตามเก็บส่วนที่ยังไม่สำเร็จ

## เลือกจากข้อจำกัดที่วัดได้

เริ่มจากปริมาณข้อมูลต่อวัน ขนาดรวม รูปแบบ Query เวลาที่ต้องเสร็จ งบประมาณ และทักษะทีม ตรวจ Query/Index, รูปแบบไฟล์ และการแบ่งงานก่อนเพิ่มระบบกระจาย

แยกปัญหา CPU, RAM, Disk I/O, Network, Lock และการรับข้อมูล เพราะแต่ละเรื่องแก้ต่างกัน บางครั้ง Query ที่เหมาะสมหรือเปลี่ยน Grain รายงานก็ช่วยได้โดยไม่ต้องเปลี่ยนทั้งสถาปัตยกรรม

## เชื่อมกับ Workshop Kaggle

Dataset Olist ช่วยฝึก Modeling, Cleansing และ Migration ได้ แต่ชื่อ Kaggle หรือการมีหลาย CSV ไม่ได้พิสูจน์ว่าต้องใช้ระบบ Big Data

ถ้าจะทดลอง scale ให้สร้างข้อมูลจำลองที่รักษาคีย์และการกระจายอย่างมีเหตุผล ระบุว่าข้อมูลถูกสร้างขึ้น ไม่คัดลอกแถวให้คีย์ซ้ำแล้วนับเป็นธุรกรรมจริง วัดเวลา throughput และต้นทุนก่อน–หลังการเปลี่ยนวิธี

## แบบฝึกหัด

กำหนดงานสองแบบ: รายงานยอดขายเสร็จก่อนเช้า กับตรวจเหตุผิดปกติภายในหนึ่งนาที ระบุความสดที่ยอมรับ การรับข้อมูลซ้ำ/มาช้า และวิธีประมวลผลที่เรียบง่ายที่สุดสำหรับแต่ละงาน ยังไม่ต้องเลือกชื่อผลิตภัณฑ์
